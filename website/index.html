Built for precise input editing

Your run. Your inputs.
Your frame data.

OpenTAS64 focuses on making controller input visible, editable and repeatable — while keeping the emulator itself separate.

▥

Vertical Piano Roll

See controller buttons as columns and frames as rows. Edit individual inputs directly in the timeline.

⌖

Frame-by-frame editing

Select, insert and remove frames, then edit button states and analog stick X/Y values.

⇄

Mupen64Plus bridge

A dedicated input plugin connects the editor to Mupen64Plus through a local TCP connection.

Ⅱ

Lockstep controls

Frame delivery waits for an input-poll acknowledgement before the next TAS input is sent.

▤

Native project files

Save and load versioned .otas projects, with TAS data kept independent from the UI and emulator.

⌘

Cross-platform setup

A Python bootstrapper detects the operating system, installs supported dependencies and builds from source.

Under the hood

A small bridge.
A clear boundary.

OpenTAS64 does not replace the emulator. The desktop editor sends frame-indexed controller states to the Mupen64Plus input plugin. The plugin makes the queued state available through the emulator's normal input callback.

The connection is restricted to the local machine. The editor and plugin use a versioned protocol with one input frame in flight at a time.

CONNECTION FLOWPROTOCOL V2
// Desktop editor
send(frameIndex, controllerState);
waitFor(inputPollAck);

// Mupen64Plus input plugin
on GetKeys(controller) {
  waitFor(queuedInput);
  latch(controllerState);
  acknowledge(frameIndex);
}

// Local-only endpoint

Synchronization note
The current acknowledgement confirms that Mupen64Plus consumed an input state in its GetKeys callback. It does not confirm that the corresponding video frame has finished rendering. Step Frame is currently one acknowledged input poll, not a guaranteed completed video frame. Pause behavior and multi-frame playback still need manual runtime verification.
